## Outcome and non-negotiable boundaries

The actual `/operating-picture` must render one identifiable card per **active domain**, each showing its own genuinely sourced headline metric, comparable trend, and highest-priority attention, plus an honest empty state for a domain without data. A domain with existing data but no trend/attention contract is a missing capability, not an empty-data success. Never substitute five freshness tiles, one global attention item repeated across cards, mock data, invented periods, prices, currency, or a synthetic trend. Preserve useful existing Operating Picture functionality, permissions, error truth, and navigation. App-facing values must come from existing reporting-layer publications or new explicit reporting contracts, never direct landing reads.

M700 means all additions **and** deletions including worker tests/docs/generated changes; the full outcome gets at most two actual implementation attempts total. Neither raising that cap, excluding generated files, dropping gates, treating `not_supported` as the required facet for a populated domain, nor spending two attempts as preplanned feature halves is authorized. Honest prerequisite work may be proposed for owner disposition; it is not delivery of this item and does not reset its attempt budget.

## Evidence and decisions still needed before freezing a release

1. **ACTIVE membership has no existing domain contract.** Current page hardcodes five freshness categories, not active domains (`apps/web/frontend/app/operating-picture/page.js:200`). Runtime registers four built-ins—finance, utilities, overview and homelab—plus extension packs (`packages/pipelines/composition/builtin_packs.py:16`, `packages/platform/capability_registry.py:29`), but `CapabilityPack` has no `enabled` field (`packages/platform/capability_types.py:151`). External installation/disable state and adapter active state are different mechanisms; `/control/packs` is admin-only (`apps/api/routes/pack_routes.py:1`). The native planner proposes loaded packs with sources and excluding overview, but that remains an unadopted design proposal, not an existing ACTIVE contract; extension loading and disabled external installations make it insufficiently established. **Owner must choose the authoritative domain registry/state, mapping of built-ins and extensions, disabled semantics, and permission-safe way to expose it to readers.** A no-data active domain must remain enumerable; membership cannot be inferred from the presence of report rows.
2. **The per-domain canonical reporting contract is incomplete.** Finance monthly cashflow exposes net by booking month but no currency (`packages/domains/finance/pipelines/transaction_models.py:93`; `transformation_transactions.py:258` groups by month alone). Utility monthly trend sums by month and type then chooses `ANY_VALUE(currency)` (`packages/domains/utilities/pipelines/transformation_utilities.py:455`). The overview's currency is derived from utility rows, not finance (`packages/domains/overview/pipelines/transformation_overview.py:100`). Therefore the native plan's suggestion to label finance using overview currency, or detect all mixed utility currency only after reading the already-aggregated trend, is **rejected**. Establish a reporting-layer currency-preserving/single-currency invariant with evidence or extend its contract; otherwise display no claimed currency or safe aggregate and do not call the outcome complete. For multiple currencies, define selection/grouping and comparison without adding unlike values.
3. **Homelab source data does not establish the requested trend or domain attention.** Current service/backup/storage/workload reports exist (`packages/domains/homelab/manifest.py:55`), and current homelab ROI has service counts (`packages/domains/overview/pipelines/overview_models.py:75`), but a current snapshot and a seven-day rolling average do not prove a comparable historical series. The existing attention mart refresh emits finance and utilities only (`packages/domains/overview/pipelines/transformation_overview.py:280`); it does not establish whether homelab has no attention. Owner must decide canonical homelab metric, comparable historical publication/time grain and operational attention/ranking source, including provenance and true absence semantics. A missing prior observation on a supported trend is `no history`; a missing publication or unsupported capability is not an empty observation. No fabricated historical points or source freshness surrogate.
4. **Resolve priority along the whole existing path before implementing 'top'.** Overview schema says 1 low, 2 medium, 3 high (`overview_models.py:18`); its transformation orders descending, including expired/near-renewal priority 3. `attention_records.py:87` asks the published-store path to order ascending, whereas the warehouse fallback reads the descending mart (`reporting_service.py:1335`). Current `/reports/attention-items` and `to_jsonable` pass integer severity without a visible normalization (`apps/api/routes/report_routes.py:564`, `apps/api/support.py:455`); Operating Picture sorts ascending and calls 1 urgent, while `/review` sorts descending and calls 3 failed. This observation concerns this overview publication; do not assume individual-attention APIs share the scale. Owner must bind the canonical source-specific severity mapping, deterministic tie-break and exact `source_domain` association, and prove published and warehouse paths agree. Unknown/unmapped domains never leak into another card.
5. **Layout and permissions:** retain the existing hero and other established functionality unless a reviewed product decision explicitly changes it; add a semantically labelled, responsive card grid as the proposed location. Confirm exact domain drill-down links against existing route/auth behavior, including restricted reports and opaque attention identity. Existing page advertises reader access but requests admin-only source freshness; this is a code inference, not a measured browser result. A new composition route must not bypass publication-level permissions or widen token access. Use permission-aware independent facet failures, not a catch-all empty state. Test actual reader/operator/admin behavior and isolated 401/403/transport/partial failure before binding a route or permission design.
